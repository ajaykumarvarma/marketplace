# Existing Site UI/UX Slop Refinement Instructions for Emergent

## Role

Act as a senior product designer, frontend engineer, UX reviewer, accessibility reviewer, and design-system maintainer working on an **already-built, working website**.

This is a **refinement and quality-control task**, not a redesign.

Your goal is to inspect the complete existing website, identify genuine UI/UX slop, AI-generated design habits, inconsistent styling, weak responsive behavior, accessibility problems, and frontend quality issues, then fix them **without damaging the current product, brand, layout logic, functionality, content, or user flows**.

The website already exists and already has an intended visual direction. Treat the existing project as the source of truth unless there is clear evidence that a specific implementation is defective.

---

# 1. NON-NEGOTIABLE PRESERVATION RULE

**Refinement preserves. Redesign replaces. This task is refinement only.**

Do not secretly redesign the website while claiming to polish it.

Preserve unless a change is clearly necessary:

- existing brand identity
- logo and brand assets
- established color direction
- established light/dark theme choice
- existing font families when they are already intentional and readable
- information architecture
- route structure
- page purpose
- existing content meaning
- existing navigation model
- existing features
- business logic
- APIs
- authentication
- database behavior
- payments
- analytics
- forms and validation logic
- integrations
- data contracts
- application state behavior
- SEO-relevant content and metadata
- URLs
- working interactions
- intentional product-specific visual details

Do not introduce a new visual world.

Do not change the site into another common aesthetic such as generic minimalist SaaS, glassmorphism, cyberpunk, neo-brutalism, beige editorial, Apple-like, Linear-like, Stripe-like, or any other template style unless that style is already clearly established by the project.

When uncertain whether something is intentional or defective, preserve it.

---

# 2. CHANGE SAFETY

Before editing, inspect the project and understand what already works.

Use the smallest correct change.

Prefer this order:

1. fix a local defect locally;
2. fix a shared component only when the same defect genuinely affects every use of that component;
3. adjust a design token only when the token itself is the root cause and the global result is safe;
4. avoid broad rewrites when a focused change solves the problem.

Do not replace entire pages or component systems just to remove several styling issues.

Do not replace the UI library, CSS framework, routing system, icon library, animation library, or application architecture unless the current project is actually broken and the replacement is unavoidable.

Do not add dependencies for effects or behavior that the existing stack can handle.

Do not remove functionality to simplify the design.

Do not hide important controls on mobile simply because they are difficult to fit.

Do not delete content only to make a layout cleaner.

Do not invent testimonials, metrics, customer logos, claims, pricing information, product capabilities, or other factual content.

Do not change factual copy unless required to fix a clear usability problem. Preserve product terminology.

---

# 3. FIRST PASS: DISCOVER THE ENTIRE WEBSITE

Do not begin by randomly editing the homepage.

First inspect the repository and determine:

- frontend framework and styling approach
- app/router structure
- every user-facing route
- shared layouts
- shared navigation
- header and footer
- reusable UI components
- page-specific components
- design tokens
- CSS variables
- theme files
- typography configuration
- icon system
- animation/motion system
- breakpoints
- assets
- forms
- dialogs
- dropdowns
- tables
- cards
- loading states
- empty states
- error states
- responsive variants

Build an internal route and component checklist.

Audit the full website, not only the visible page currently open in preview.

If routes are generated dynamically, inspect the routing code and representative instances.

Classify each surface by what the visitor is doing:

- **Persuade**: landing, marketing, pricing, promotional pages
- **Operate**: dashboards, tools, authenticated app screens, settings
- **Read**: docs, articles, guides, help content
- **Experience**: portfolio, gallery, showcase, immersive presentation

Do not apply the same density, typography, motion, or composition rules blindly to every surface.

---

# 4. ESTABLISH EXISTING VISUAL TRUTH

Before changing global styles, inspect representative sources of the site's existing visual language:

- global CSS
- theme/tokens
- root layout
- primary button
- input/form controls
- navigation
- representative card/container
- one marketing page if present
- one product/application page if present
- existing brand assets

Infer the current system:

- primary and secondary colors
- neutral surfaces
- semantic colors
- spacing rhythm
- corner-radius scale
- border/elevation strategy
- typography roles
- container widths
- common component states
- icon family
- motion style

Treat repeated, coherent project conventions as intentional.

Do not "fix" something simply because it differs from a generic design recommendation.

A detector-like rule is evidence to inspect, not an automatic instruction to delete.

---

# 5. WHAT COUNTS AS A REAL SLOP ISSUE

Fix a pattern only when it is actually hurting clarity, hierarchy, usability, consistency, responsiveness, accessibility, performance, or the established visual language.

Common issues to inspect include:

## Containers and cards

Look for:

- unnecessary cards around every content group
- cards nested inside cards
- repeated same-size icon + heading + text cards used as default page scaffolding
- borders, backgrounds, and shadows all layered on the same simple container without purpose
- excessive panelization that fragments related content
- decorative containers used where spacing and typography would communicate grouping better

Do not remove useful cards that communicate real grouping, interaction, selection, state, or elevation.

Prefer proximity, spacing, alignment, dividers, and surface hierarchy before adding more boxes.

Never flatten a useful interface merely to satisfy a "fewer cards" rule.

## Decorative AI habits

Inspect for unjustified:

- gradient text
- purple/blue/cyan AI-style gradients
- random glow halos
- blurred colored blobs
- glassmorphism
- excessive backdrop blur
- decorative grid backgrounds
- repeated stripe backgrounds
- fake terminal styling
- decorative monospace usage
- oversized rounded icon tiles
- thick colored side borders
- giant radii on ordinary components
- repeated pill shapes everywhere
- hard offset shadows outside an intentional matching style
- decorative progress rings or tiny fake charts that do not communicate real data
- emoji or Unicode characters used as inconsistent replacement icons

If any such treatment is clearly part of the existing brand and is used deliberately, preserve it.

The goal is not to ban visual effects. The goal is to remove effects that have no job.

## Repetition

Inspect whether repeated sections are truly equivalent.

Avoid page structures that feel mechanically generated because every section uses:

- identical three-column cards
- identical icon tiles
- identical centered heading + paragraph + grid
- identical fade-up entrance
- identical spacing everywhere

Repetition that improves recognition is good.

Only introduce variation when content importance or purpose actually changes.

---

# 6. LAYOUT AND SPACING

Do not move elements before understanding the structural problem.

Check:

- reading order
- primary task path
- grouping
- alignment
- density
- whitespace
- section rhythm
- container widths
- responsive reflow
- long content
- empty content
- overlays
- sticky elements
- overflow
- visual versus DOM order

Use proximity to group related information.

Related elements should generally be closer together than unrelated sections.

Avoid one spacing value repeated everywhere until the page has no hierarchy.

Headings should visually belong to the content below them rather than the section above.

Prefer an existing spacing scale. If the project has no scale and inconsistent arbitrary values are causing visible problems, normalize them conservatively.

Do not normalize every intentional optical adjustment.

Do not make every section equally tall or equally padded.

Do not create huge empty areas simply to look "premium."

Do not make dense product screens excessively spacious if density helps users perform tasks.

---

# 7. TYPOGRAPHY

Improve typography **inside the existing identity**.

Do not replace the site's fonts merely because another font is trendier.

Check:

- role hierarchy
- heading/body differentiation
- repeated roles using inconsistent sizes
- body readability
- line length
- line height
- wrapping
- very long headings
- narrow mobile layouts
- localization expansion
- font loading
- fallback behavior
- excessive negative tracking
- unnecessary all-caps text
- tiny meaningful text

General quality targets where compatible with the existing design:

- ordinary body copy around 16px / 1rem
- genuinely secondary text may be smaller but must remain readable
- prose usually around 45–75 characters per line
- clear visual difference between display, H1, H2, H3, body, labels, and metadata
- avoid tracking tighter than approximately -0.04em
- avoid giant display text that overwhelms the viewport or breaks on mobile

Do not force marketing typography rules onto dense product UI.

Do not force display fonts into buttons, tables, labels, inputs, or data-heavy product surfaces.

If one existing font family already works well across an application UI, keeping one family is acceptable.

---

# 8. COLOR, SURFACES, BORDERS, AND DEPTH

Preserve established brand colors.

Use color intentionally for:

- hierarchy
- primary action
- selection
- status
- wayfinding
- meaningful atmosphere

Do not spend the primary action color on random decoration.

Keep success, warning, error, information, selected, disabled, and focus meanings consistent.

Avoid generic gray text on strongly colored surfaces when a foreground-derived/tinted value gives clearer readable hierarchy.

Check contrast rather than guessing visually.

Target at least:

- 4.5:1 for normal text
- 3:1 for large text
- 3:1 for important controls, icons, and focus indicators where applicable

Do not globally remove all shadows or borders.

Depth should communicate hierarchy or state.

For a simple surface, avoid automatically combining a visible border with a large diffuse shadow.

Avoid glow halos pretending to be elevation.

Do not force all cards to the same radius.

Do not convert ordinary buttons and containers into pills unless their role genuinely suits a pill shape.

If the current radius system is coherent, keep it.

---

# 9. NAVIGATION AND INFORMATION ARCHITECTURE

Preserve the existing information architecture unless a clear usability bug exists.

Do not rename navigation items casually.

Check:

- current page indication
- navigation consistency
- mobile navigation
- keyboard access
- submenu behavior
- dropdown clipping
- back/close behavior
- selected states
- touch usability

Do not move major pages or actions simply to make the design look different.

Familiarity is valuable in application UI.

Standard controls should behave like standard controls.

Avoid unusual interactions that make users relearn basic actions without a product-specific reason.

---

# 10. FORMS AND INTERACTIVE COMPONENTS

Preserve existing functional logic.

Check every relevant component for appropriate states:

- default
- hover
- focus
- active
- selected
- disabled
- loading
- error
- success

Forms should have persistent labels where needed.

Place validation feedback near the related field.

Do not use placeholders as the only label.

Do not replace working accessible native behavior with a custom visual imitation.

Use buttons for actions and links for navigation unless the existing framework abstraction correctly handles semantics.

Icon-only controls need accessible names.

Do not remove focus indicators.

Avoid generic "Yes", "No", "OK", or "Submit" when the actual action needs to be clear, but do not rewrite product copy unnecessarily.

---

# 11. MODALS, POPOVERS, DROPDOWNS, AND OVERLAYS

Do not use a modal just because it is convenient to implement.

Preserve existing modals that are appropriate for focused or interruptive tasks.

Check whether oversized or complex modal workflows should already be full surfaces, but do not perform a major information-architecture change unless there is a serious usability problem.

Make sure dropdowns, tooltips, popovers, and menus are not clipped by parent overflow.

Check:

- z-index behavior
- focus trapping where required
- Escape/close behavior
- click/tap outside behavior where appropriate
- scroll locking
- mobile presentation
- keyboard navigation

Do not introduce brittle z-index hacks when structure can solve the issue cleanly.

---

# 12. RESPONSIVE QUALITY: ADAPT, DO NOT AMPUTATE

Responsive design is not desktop scaled down.

Inspect every route at representative widths, including approximately:

- 320px
- 375px
- 430px
- 768px
- 1024px
- 1280px
- wide desktop

Also inspect intermediate widths where the actual design breaks.

Preserve core functionality on small screens.

Instead of hiding important features:

- stack
- reflow
- collapse secondary groups
- use progressive disclosure
- adapt navigation
- make tables intentionally scrollable or transform them where appropriate
- reorganize controls
- use container-aware behavior

Do not rely on hover for required functionality.

Provide usable touch interaction.

Aim for roughly 44×44px effective touch targets for important interactive controls when practical.

Use adequate mobile gutters. Content should not touch viewport edges.

Check:

- horizontal overflow
- long URLs
- long words
- long labels
- buttons wrapping
- input widths
- table overflow
- images
- absolute positioning
- sticky elements
- viewport units
- orientation changes
- browser zoom

Use content-driven breakpoints where practical rather than changing the architecture only because a device category name changed.

---

# 13. MOTION

Do not add animation simply to prove the site was polished.

Preserve useful existing motion.

Motion should mainly:

- acknowledge an action
- explain state change
- preserve continuity
- reveal a relationship
- direct attention at a meaningful moment
- support an already-established branded experience

Avoid:

- identical fade-up animation on every section
- unnecessary scroll reveals
- constant floating elements
- decorative bouncing
- elastic/bouncy transitions by default
- repeated hover lift on every card
- fake blinking cursors
- meaningless pulsing dots
- auto-moving elements that distract from reading or task completion

Routine product interactions should remain fast.

Do not make users wait through page-load choreography on application screens.

Keep content visible by default. Failed animation JavaScript must not leave important content hidden.

Avoid casually animating layout-driving properties when a cheaper technique can communicate the same result.

Respect `prefers-reduced-motion`.

Do not add a new motion dependency if the current stack already supports the needed behavior.

---

# 14. COPY AND CONTENT

This is primarily a design refinement task, not a copy rewrite.

Preserve factual meaning, product terminology, SEO intent, legal meaning, feature descriptions, pricing, and claims.

Only improve visible wording when it is clearly:

- confusing
- redundant
- inconsistent
- misleading
- too vague to understand an action
- exposing internal technical errors to ordinary users

Say an idea once.

Remove redundant helper text only when removing it does not remove useful context.

Actions should clearly describe outcomes.

Errors should explain what failed and, when possible, what the user can do next.

Empty states should distinguish between first use, no results, filtering, permission issues, and actual failure when the application already supports those distinctions.

Never fabricate reasons, progress, timing, metrics, or product capabilities.

---

# 15. ACCESSIBILITY

Audit accessibility as part of quality assurance, not as an excuse to flatten the visual design.

Check:

- semantic HTML
- heading order
- button/link semantics
- labels
- accessible names
- keyboard navigation
- focus visibility
- logical tab order
- dialog focus behavior
- contrast
- non-color state cues
- image alt behavior
- dynamic-state announcements where applicable
- zoom up to 200%
- reduced motion
- touch target usability

Do not change heading levels just to achieve a visual size. Use styling for appearance and semantic heading levels for structure.

Decorative images should not create noisy screen-reader output.

Meaningful images need useful alternative text.

---

# 16. REAL CONTENT AND EDGE CASES

A design that works only with ideal demo data is not finished.

Without changing actual production data or backend contracts, inspect/test representative UI behavior for:

- very long names
- long headings
- long descriptions
- long email addresses
- missing optional images
- empty lists
- zero results
- one result
- many results
- large numbers
- narrow containers
- long button labels
- error states
- loading states
- permission-limited states where applicable

Fix visual overflow at the component/layout level.

Prefer flexible layout over hard-coded widths for text content.

Do not truncate information that users genuinely need unless a discoverable full-value path already exists.

---

# 17. IMAGERY AND ICONS

Preserve real, intentional imagery and brand assets.

Check for:

- broken images
- empty sources
- distorted aspect ratios
- missing dimensions causing layout shift
- poor responsive sizing
- irrelevant placeholder art
- inconsistent icon families
- random emoji used as UI icons

Do not replace a meaningful image with decorative abstract shapes.

Do not generate fake illustration merely because a section feels empty.

Real product screenshots, real imagery, meaningful diagrams, or intentional whitespace are all preferable to filler graphics.

Keep icon stroke, weight, size, and optical alignment consistent with the established system.

---

# 18. PERFORMANCE

Do not perform speculative rewrites in the name of optimization.

Only fix performance issues that are visible or supported by evidence.

Check for obvious frontend problems such as:

- oversized images
- image layout shift
- unnecessary font weights
- unused heavy visual dependencies
- excessive DOM wrappers from decorative UI
- expensive always-running animations
- repeated unnecessary effects
- obvious rerender or layout-thrashing patterns encountered during this UI pass

Do not sacrifice functionality, accessibility, or visual identity for tiny theoretical gains.

Do not lazy-load content that is required immediately above the fold.

---

# 19. CODE-LEVEL UI AUDIT

Inspect the source in addition to the rendered result.

Look for suspicious patterns such as excessive or inconsistent use of:

- very large border radii
- `rounded-full` on non-pill components
- large shadows
- decorative blur
- backdrop blur
- gradient text
- arbitrary colors
- arbitrary spacing
- arbitrary font sizes
- negative tracking
- fixed dimensions on text-heavy containers
- repeated hard-coded component variants
- absolute positioning
- `overflow-hidden`
- excessive z-index values
- duplicated button/input/card implementations
- dead styles
- stale classes
- unused imports
- temporary debug code

These are **inspection signals**, not automatic delete rules.

Never run a blind search-and-replace that could damage intentional styles.

Fix the cause at the narrowest safe level.

If multiple components clearly implement the same visual role inconsistently, consolidate carefully around the already-established best version.

Do not create a large abstraction for a one-off exception.

---

# 20. ANTI-OVER-CORRECTION RULES

After fixing slop, the site must still have character.

Do NOT:

- make everything white
- make everything gray
- remove every shadow
- remove every gradient
- remove every animation
- remove every card
- square every corner
- flatten every hierarchy
- make every section look identical
- shrink everything
- make every font weight light
- turn every page into a dashboard
- turn every page into a landing page
- replace all visual interest with whitespace
- redesign just to achieve novelty

A design effect is allowed when the current product or brand earns it.

The question is not "Is this pattern on a slop list?"

The question is:

**Does this specific implementation help this specific product, page, user task, hierarchy, and visual identity?**

If yes, preserve or refine it.

---

# 21. FUNCTIONAL PROTECTION

UI polish must never break the product.

Do not modify backend/business logic unless a frontend defect cannot otherwise be fixed.

Specifically protect:

- API endpoints and request shapes
- database models
- auth/session logic
- permissions
- payment flows
- analytics/tracking
- environment variables
- secrets
- integrations
- server configuration
- routing behavior
- form submission behavior
- validation rules
- persisted user data
- state management semantics

Before changing a shared interactive component, inspect its usages.

After changing it, test representative usages.

Do not change an event handler merely to solve a visual problem unless it is directly causing the UI defect.

---

# 22. EXECUTION STRATEGY FOR EMERGENT

Work in bounded passes.

Do not spend the entire run repeatedly polishing the same page.

## Pass A: Inspect

Discover routes, components, visual system, and major problems.

Do not make large global changes before understanding the existing design.

## Pass B: Prioritize

Internally classify findings:

- P0: functionality blocked or content inaccessible
- P1: major UX, responsive, accessibility, or consistency issue
- P2: visible design-system/slop issue
- P3: minor cosmetic cleanup

Fix higher-impact problems before cosmetic ones.

## Pass C: Shared foundations

Only where justified, fix safe shared problems such as:

- inconsistent tokens
- common button/input states
- global overflow
- global typography role drift
- shared navigation defects

## Pass D: Route-by-route refinement

Review every discovered user-facing route.

Make only necessary page-specific corrections.

## Pass E: Responsive and interaction pass

Check representative mobile, tablet, desktop, keyboard, and touch behavior.

## Pass F: Verification

Run/build/test the project using the project's existing tooling.

Check console/runtime errors and fix regressions caused by this work.

Perform one consolidated visual verification pass across representative desktop and mobile pages.

If that pass reveals defects caused by the changes, fix them in one batch and do at most one final confirmation pass.

Do not enter an endless polish loop.

Do not deploy automatically unless deployment was already explicitly requested elsewhere.

---

# 23. REGRESSION CHECKLIST

Before finishing, verify:

## Product safety

- existing routes still work
- navigation still works
- forms still work
- auth-related UI still works
- important actions still work
- no working feature was removed
- no factual content was invented
- no backend contract was changed unnecessarily

## Visual consistency

- brand identity still looks like the same product
- colors remain coherent
- typography remains coherent
- components with the same role look and behave consistently
- spacing has meaningful rhythm
- hierarchy is clearer
- unnecessary slop is reduced
- distinctive intentional details remain

## Responsive

- no accidental horizontal scrolling
- mobile navigation works
- important functionality remains available
- long content does not destroy layout
- overlays are not clipped
- intermediate widths are usable
- wide layouts do not stretch awkwardly

## Accessibility

- keyboard focus remains visible
- tab order is sensible
- labels/accessibility names exist where needed
- contrast is reasonable
- semantic structure is preserved/improved
- reduced-motion behavior is respected

## Runtime

- application builds/runs
- no new console errors
- no broken imports
- no missing assets
- no components hidden due to failed animation
- no obvious layout shift introduced by this work

## Code hygiene

- no accidental duplicate components
- no temporary debug code
- no obsolete styles left by the edits
- no unnecessary dependency added
- no broad unrelated formatting churn

---

# 24. DECISION RULE WHEN YOU ARE UNSURE

Use this decision hierarchy:

1. protect functionality;
2. protect product truth;
3. protect existing brand identity;
4. protect established user mental models;
5. improve accessibility and responsiveness;
6. improve hierarchy and consistency;
7. remove unjustified decorative slop;
8. clean code only where it supports the above.

When two possible fixes exist, choose the one with the smaller blast radius.

When a global change could unpredictably alter many pages, prefer scoped changes unless you have inspected every affected usage.

When an unusual visual choice is consistent, intentional, and usable, do not normalize it merely because it is unusual.

---

# 25. FINAL INSTRUCTION

Do not respond with a redesign proposal.

Do not only list issues.

Inspect the existing project, make the safe refinements in the source code, verify them, and preserve everything that already works.

The desired outcome is:

**the same website, same product, same identity, same functionality — but cleaner, more intentional, more consistent, less AI-generated, more responsive, more accessible, and more production-ready.**

The finished result should feel like a careful senior designer and frontend engineer refined the existing site, not like an AI replaced it with another template.

At completion, give only a concise report containing:

1. routes/pages reviewed;
2. major slop/UX issues corrected;
3. shared components or tokens safely refined;
4. responsive/accessibility issues corrected;
5. verification performed;
6. any issue intentionally left unchanged because changing it would risk the current design or functionality.
